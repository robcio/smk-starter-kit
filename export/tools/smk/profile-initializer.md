# SMK Core profile initializer — schema 1 / generator 1

C10.5 implements step 4 of document 11 §12, not a component named SMK-C05. This is an offline developer tool, not a Statamic addon, runtime installer, release exporter or content migration system. The workbench now includes the C10.6 Page Builder and C10.7 SEO integration. Its reviewed compiled builder fieldset was integrated explicitly; the live section allowlist is the developer-owned `SectionRegistry::TYPES`. The initializer profile remains inactive: no generated profile/render-map, module imports or ownership ledger have been activated. Preparing the tool does not authorize applying a profile to this workbench. See [Page Builder](page-builder.md) and [SEO](seo.md).

## Read-only commands

Run with the installed PHP runtime and the actual Node executable on PATH. Composer's installed package metadata supplies the actual Laravel/Statamic versions; PHP_VERSION supplies PHP; a fixed, shell-free `node --version` supplies Node. Manifest data never supplies a command or network request. Neither command boots Laravel or loads .env.

```sh
php tools/smk/init-profile.php --root=/absolute/isolated/project --validate
php tools/smk/init-profile.php --root=/absolute/isolated/project > /private/tmp/reviewed-smk-plan.json
```

The default is plan/dry-run. Root is mandatory, canonicalized independently of manifest data. Profile and manifest options are explicit relative paths (`--profile=...`, repeat `--manifest=...`); no glob discovery or automatic dependency installation. Plan prints a JSON envelope with `approval_sha256` and `plan`. Every operation includes full before/after bytes, a full replacement diff (not abbreviated context), owner, POSIX metadata, root/component identities, hashes, create/replace/no-op, missing predecessors and required directories/space. The plan also records the tool hashes, observed platform, source identities and recovery policy. It does not write anything to the root.

Do not publish plan/journal files. Their managed generated contents are neutral technical data, but absolute local paths and previous generated bytes are included. The plan is JSON; inspect `operations.*.diff` and metadata before approving the complete hash. It is not an implicit approval of a future replan.

## Format and deliberately limited MVP

`resources/smk/core/manifest.yaml` is the required `smk.core`, product version **0.1.0**. Product SemVer is independent of `manifest_schema=1`, `core_contract_version=1`, `profile_schema=1` and generator version 1. Schema keys are strict, including nested mappings. YAML uses Symfony YAML with invalid-type rejection; duplicate keys are rejected. Objects, shell hooks and unknown keys are unsupported.

Module manifests follow document 11 §7.2: requires.core/modules/edition/platform/asset_containers; provides.blocks/collections/blueprints/fieldsets/asset_containers; views; frontend.css/js; contributions; conflicts; owned_paths; licenses. Schema 1 requires `core_contract_version: 1`. Declarations for collections/blueprints/fieldsets/containers are explicit `{handle, path}` records; collections may declare `route` for exact case-insensitive route collision checking. Block declarations have owned fieldset/partial, variants and default. This validator does not solve semantic overlap of arbitrary routing patterns.

`owned_paths` is a list of individual existing regular source files, not directories or globs. This stricter MVP subset avoids hidden ownership of undeclared files. Sources referenced by provides/views/frontend must be explicitly owned. Case-insensitive duplicates, overlapping ownership, hardlink aliases, handle/route conflicts, missing providers/dependencies and cycles fail closed. Core/Brand namespaces and known Core fieldsets are reserved from modules. License strings are policy references, not license keys, network locations to fetch or an assertion of distribution rights. `project-license-policy` refers to the existing composer.json `license: proprietary`; the tool does not change that policy or grant release rights.

`contributions` is empty in this MVP: nonempty contributions are refused until their merge semantics are implemented. `conflicts` supports explicit IDs only; executable predicates are refused. Valid and invalid module declarations are fixtures, not installed business modules. `--validate` can check an explicitly selected fixture profile; **generation/apply accepts the neutral Core profile with an empty modules list only**.

Core adds `generated_outputs`, an exact declaration of the built-in five-path allowlist below. It must match the built-in list; modules cannot declare this key or expand write authority:

1. `resources/fieldsets/smk_page_builder.yaml`
2. `resources/smk/generated/profile.json`
3. `resources/smk/generated/render-map.json`
4. `resources/css/generated/modules.css`
5. `resources/js/generated/modules.js`

The current Core manifest declares Hero, Rich Text and CTA, with their owned fieldsets and views. The compiler emits these three sets in the builder fieldset and three entries in the render-map. Editor-facing labels are Polish; handles, variant values and import paths stay unchanged. Core has no module frontend contributions, so generated module CSS/JS still contain only neutral comments. The earlier empty-block generation described the C10.5 input before C10.6, not the current manifest.

The workbench's existing `smk_page_builder.yaml` is a reviewed compilation artifact, not evidence of initializer ownership or profile activation. When changing its presentation metadata, regenerate the proposed bytes via a read-only plan in an isolated input copy and compare them before integrating that artifact. Do not run apply on the workbench or fabricate a ledger to adopt its existing file. The normal unknown/unowned-target refusal still applies. No business module, content migration engine or runtime installer has been added.

## Apply: controlled context is mandatory

Only isolated test roots were exercised during C10.5. **Do not run apply on the actual workbench as part of implementing/testing this stage.** A later operator must obtain separate authorization to activate a profile.

For an authorized offline isolated root, after reviewing the exact saved plan:

```sh
php tools/smk/init-profile.php --root=/absolute/isolated/project --apply=/private/tmp/reviewed-smk-plan.json --accept=EXACT_APPROVAL_SHA256 --offline-exclusive
```

The envelope and a bare plan are both accepted; `--accept` is always the hash of the inner plan. `--offline-exclusive` is the operator's explicit attestation that:

- no request, scheduler, worker, watcher, editor or other process reads or writes the project during apply/recovery;
- the caller exclusively controls its directory tree and account, and the project root is not a public document root;
- only ordinary generator-owned files with POSIX owner/group/mode/second-resolution mtime are involved; special ACLs, xattrs and unsupported metadata are outside this MVP context;
- permissions/ACLs of the surrounding environment prevent another user from replacing managed paths.

The tool cannot independently discover every reader or prove the absence of another process with the same UID. **If the operator cannot establish these conditions, do not supply the flag: apply must be refused.** It does not enable maintenance mode or stop/restart any services.

PHP's pathname operations do not supply portable openat/renameat no-follow directory handles. The implementation therefore uses the contract's explicitly controlled-context alternative, not a claim of protection against a hostile concurrent process. It checks lstat identity, type, UID/GID, permissions, nlink, ancestor chain and hashes repeatedly. This narrows mistakes and detects tested swaps; it cannot close a hostile last-instant pathname race. Its lock is cooperative only. The offline/exclusive constraint must remain in force during recovery too.

Managed paths use portable relative ASCII segments, no absolute/drive/UNC path, dot segment, empty segment, backslash, percent encoding, streams, control characters, glob, symlink (including internal/dangling links), special object or shared hardlink. Existing components must belong to the invoking UID and must not be group/world writable. New outputs must be on the same filesystem. The actual canonical root can be selected intentionally through a user path alias; its subsequent filesystem identity cannot change. Existing ancestor identities are recorded, not just string prefixes.

## Staging, journal and recovery

The deterministic `transaction_id` inside the reviewed plan identifies the plan, not an execution attempt. Each non-no-op apply allocates a fresh random `attempt_id` after acquiring the lock and rejecting unresolved work. Only that attempt may create its private `tx-<attempt_id>` directory; an existing directory at that exact path is still a collision and is refused. Journal schema 2 binds the attempt to the accepted plan hash. A verified `restored` attempt remains archived, so the same still-current plan can start a new attempt without changing the plan or touching previous backups/journals. A rollback that restored a file under a new inode makes the old plan stale: replan and review it normally; the intended output bytes remain deterministic. Random attempt identities never enter the plan or generated outputs.

Recovery also accepts existing schema 1 journals, which used `tx-<plan transaction_id>`, without moving or discarding their evidence. `restored[path]` is a durable restore **intent** until that exact identity is observed at the target with predecessor hashes/metadata. If the target still has the known after identity, recovery restages the verified backup and retries, retaining prior restore staging. If the intent identity already occupies the target, recovery does not replace it again. A crash before or after rename is therefore classified from real file identities, not from the presence of a journal key. Immediately before restore rename, root/parents, the target after identity and restore staging are checked again; a detected foreign modification is preserved and leaves recovery blocked. The controlled-context TOCTOU limit still applies.

Private `smk-init-state/` (0700) is fixed auxiliary storage outside public/. It is not a manifest-provided output path. Lock, current generation ledger and journal are private; each transaction retains a private directory with after files, backup bytes, archived journal and quarantine. Private directories protect staged files even when their eventual destination mode is 0644. The ledger identifies only the five generator-owned outputs by hash/mode/GID. It is local ownership evidence, not an external cryptographic signature or protection from an administrator forging the entire ledger.

Apply checks the accepted hash and recomputes the entire plan before preparing anything. Then it locks, rejects pending journals, stages all bytes and backups on the same filesystem, verifies the complete staged set, records prepared/applying durably, creates declared directories and activates changed files via per-file rename. Files and affected directories are fsynced; inability to fsync refuses/fails the operation. It rechecks sources and destination chains before activation and each replacement, verifies the full resulting set, and only then marks committed. There are no target truncation writes. Identical contents/state produce no-op, including the ledger, without refreshing target mtime or inode.

This is **single-file atomic replacement and recoverable set consistency**, not an atomic multi-file transaction or a live generation switch. Reads remain stopped until commit or successful recovery. No delete/uninstall exists. Empty created directories may remain after rollback; their identities are checked and they are harmless while the root remains offline.

An exception after activation starts leaves `recovery_required`; a hard process exit may leave prepared/applying. New init refuses both. It does not silently finish a partial apply:

```sh
php tools/smk/init-profile.php --root=/absolute/isolated/project --recover --offline-exclusive
```

Recovery verifies the approved plan, root/parents, every destination identity/hash and every predecessor backup **before restoring any target**. It restores predecessor bytes and supported POSIX metadata; a new file with no predecessor is renamed to private quarantine. A destination matching neither before nor after, a substituted path or corrupt backup stops recovery, preserves evidence and leaves init blocked for manual investigation. Recovery cannot guess whether a foreign change is authorized. Restored inode identities are journaled, allowing repeat recovery; final predecessor bytes/metadata are checked before marking restored. Changed inputs do not prevent rollback of a known previous generation.

Preparation failures before a journal/activation leave no changed output. Orphan staging evidence is retained; do not treat it as an activated profile. A colliding transaction directory is refused rather than overwritten. Backups/journals/quarantine are not automatically deleted; retention and manual cleanup require a separate decision. Normal init after an interrupted transaction always requires explicit recovery first.

Durability checks were exercised on the local filesystem, including real process termination. They are not certification against machine power loss, a disk/OS that misreports fsync, network filesystems, filesystem corruption, Windows or adversarial concurrent writers. Those environments must refuse activation or receive a separate implementation/review.
